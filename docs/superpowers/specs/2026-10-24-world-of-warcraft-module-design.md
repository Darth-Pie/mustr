# World of Warcraft module: characters, timeline, level race and records

Status: design approved by the owner on 2026-10-24 (conversation approval). Next: implementation plan.

## Why

The owner's guild is playing World of Warcraft: Forever, which launches on 4 November 2026.
Grats (saygrats.com), a free fan site for Forever, shows what players want from a guild site
during a fresh leveling race: a timeline of each character's levels and gear, a chart of who is
climbing fastest, records such as "first to 40", and cheers in Discord.

mustr already covers the other half of Grats: events with role sign-ups synced to Discord,
recurring events, Discord announcements, and medals that award themselves. This module adds the
game-data half, built for the owner's guild first and polished for other buyers later.

## Goals

- Members link a Battle.net account and choose which Forever characters to follow.
- mustr checks followed characters regularly and keeps a timeline of what changed.
- A level-race page shows standings, two charts and the guild's records.
- Discord gets milestone posts, and characters earn medals for gear and leveling feats.
- Everything lives in one optional **World of Warcraft** module, off by default.
- Stays inside Blizzard's API terms and Cloudflare's free plan.

## Non-goals

- Other WoW versions. Retail, Classic Era and Classic progression are not supported. The Classic
  data sections are used only to test before Forever's is published.
- Importing the in-game guild roster. Planned as a follow-up; only characters a member links
  appear.
- Maybe and Absent responses for events. A separate, smaller change.
- Members typing in their own level. All data comes from Blizzard.
- Friend groups that span organizations or join by invite link. mustr stays one org per install.
- Buyer documentation and marketing. Later, once the owner's guild has used it.

## Facts this design relies on

From mustr's code:

- Optional modules are boolean flags in `settings['modules']`, with per-module config in its own
  settings key (`src/server/modules.ts`). Star Citizen is the precedent for linking an outside game
  account to a member (`src/server/sc/`, `src/server/routes/scVerify.ts`); its routes return 404
  when the module is off.
- Secrets entered in the admin panel are stored in D1 and never sent back to the browser, only
  their presence (`src/server/config.ts`).
- `scheduled()` in `src/server/index.ts` has two crons. The 5-minute one runs the Discord
  reconcile with a budget of 40 calls (`RECONCILE_CALL_BUDGET` in `src/server/discord/sync.ts`)
  and returns early when no bot is configured. The hourly one runs DB-only sweeps (tenure and
  activity medals, recurring events).
- Medals already award themselves from `auto_grant_months` and `auto_grant_attendance`
  (`src/server/medals/`). Awards announce through the `medalAward` announcement.
- Announcements have per-event keys, templates and placeholders (`src/server/discord/announce.ts`).
- Built-in pages can be members-only or public via `settings['page_access']`
  (`src/shared/pageAccess.ts`). Built-in menu items can belong to a module and hide when it is off
  (`src/shared/nav.ts`).
- Every route is already code-split, so a library imported by one page loads only on that page.
- Timestamps are unix seconds (`unixepoch()`). Migrations are generated by drizzle-kit and bundled
  for the setup wizard (`scripts/bundle-migrations.mjs`).
- There is no test runner. `tsx` is already a dev dependency.

From Cloudflare's documentation (checked 2026-10-24):

- Free plan: 50 outgoing requests and 10 ms of CPU per invocation, and 5 cron triggers per
  account. Paid plan: 10,000 requests per invocation and 250 cron triggers per account.

From Blizzard (Developer API Terms of Use, Battle.net docs and forums, checked 2026-10-24):

- Sign-in uses the OAuth authorization-code flow at `oauth.battle.net` with the `wow.profile` scope.
  The user's token can list their characters (`/profile/user/wow`). Public character data
  (summary, equipment, status) needs only an app token from the client-credentials flow.
- Every request needs a namespace, such as `profile-classic1x-us`. Forever's has not been
  published; a forum question on 2026-09-29 had no answer from Blizzard.
- A character's data updates when the player logs out, so every change is known only to within
  "between the previous logout and this one".
- Limit: 36,000 calls an hour per client.
- Terms 2(r): data may be kept at most 30 days, except that WoW apps may instead check each
  character's status and delete it when Blizzard returns 404, `is_valid` is false, or the character
  ID has changed.
- Terms, restriction 2: players can't be charged to download an app or to use its features.
- Terms 2(m): no Blizzard trademark in the app's title or web address.

To verify during implementation: the exact field names in Classic profile responses. The parsers
are first written and tested against sample responses in Blizzard's documented shape. Once the
owner's Battle.net key exists, a capture script saves real Classic responses (with names changed)
as extra fixtures, and the parsers must pass on those too.

## Design

### Module and settings

- `ModuleFlags` gains `wow`, labelled **World of Warcraft** in Settings → Modules, default off.
- Config in `settings['wow']`:
  - `clientId` and `clientSecret` for the site's own Battle.net API client. The secret is never sent
    back to the browser.
  - `region`: `us`, `eu`, `kr` or `tw`. One region per site.
  - `namespace`: Blizzard's data section, without the region suffix. The default is a constant in
    code, set to Forever's once Blizzard publishes it. Until then admins can enter
    `profile-classic1x` to test.
- **Test connection** fetches an app token and reports success or Blizzard's error. The module can't
  be switched on until a test succeeds.
- When the module is off: every member-facing WoW route returns 404, the menu item and profile
  section are hidden, and the sweep, Discord posts and WoW medal awards stop. The admin settings
  routes stay available, because the key has to be set and tested before the module can be switched
  on. Stored data stays, subject to the retention rule below.
- Each site registers its own Battle.net client at develop.battle.net, as it does its own Discord
  app. That keeps each operator as the licensee and keeps WoW features out of anything paid.

### Data model

New migration, three tables and one column.

`wow_links`, one row per linked member:

| Column | Notes |
| --- | --- |
| `user_id` | Primary key, references `users`, cascade delete |
| `bnet_id` | Battle.net account ID, unique, so one account can't be linked by two members |
| `battletag` | Shown on the profile |
| `linked_at` | |

`wow_characters`:

| Column | Notes |
| --- | --- |
| `id` | Primary key |
| `user_id` | References `users`, cascade delete |
| `region`, `blizzard_id` | Unique together |
| `realm_slug`, `realm_name`, `name` | |
| `class_id`, `class_name`, `race_name`, `faction` | |
| `level`, `item_level` | `item_level` is the average of equipped items; null until gear is fetched |
| `guild_name` | Null when not in a guild |
| `gear` | JSON: slot → item ID, name, quality, item level. Used to detect changes |
| `followed` | False for characters listed at link time but not chosen; those are deleted after a day |
| `is_main` | At most one per member |
| `baseline_level` | Level at the first check; null until then |
| `last_login_at` | Blizzard's last-logout time |
| `last_polled_at`, `last_validated_at` | |
| `status_failures` | Consecutive failed daily status checks |
| `created_at` | |

Index on `(followed, last_polled_at)` for the sweep.

`wow_timeline`, one row per change:

| Column | Notes |
| --- | --- |
| `id` | Primary key |
| `character_id` | References `wow_characters`, cascade delete |
| `kind` | `tracking_started`, `level`, `item`, `guild_join`, `guild_leave` or `badge` |
| `level` | For `level` and `tracking_started` |
| `item_id`, `item_name`, `item_quality`, `item_level`, `slot` | For `item` |
| `tag` | `first_rare` or `first_epic` on the first item of that quality |
| `guild_name` | For guild entries |
| `badge_key` | For `badge` |
| `seen_at` | Logout time of the check that saw the change |
| `since_at` | Previous logout time; the change happened between the two |
| `created_at` | |

Index on `(character_id, seen_at)`. A jump from level 38 to 41 in one check writes three `level`
rows (39, 40, 41) with the same `seen_at` and `since_at`, so "when did this character reach level L"
is always a single lookup.

`medals` gains `auto_grant_rule` (text, null by default). The WoW rules are `wow:first_rare`,
`wow:first_epic`, `wow:all_rare`, `wow:week_of_grind` and `wow:steady_climber`.

### Code layout

Each file has one job:

- `src/server/wow/bnet.ts`: the Blizzard client. Sign-in URL, code exchange, app token (cached in
  settings until it expires), and fetches for the account's characters, a character's summary,
  equipment and status. It turns Blizzard's JSON into mustr's own types and sends an honest
  User-Agent, as the Star Citizen fetch does. No database access.
- `src/server/wow/diff.ts`: pure. Takes the stored character and a fresh observation and returns
  the updated character plus new timeline entries.
- `src/server/wow/badges.ts`: pure. Decides which badges a character has newly earned from its
  state and level history.
- `src/server/wow/records.ts`: pure. Works out standings, firsts, fastest bands and the scenic
  route from level entries.
- `src/server/wow/poll.ts`: the sweep. Picks characters, calls `bnet.ts`, runs the pure functions,
  writes rows, and hands new events to medals and announcements.
- `src/server/routes/wow.ts`: the web routes.
- Client: a `WowCharacters` component on `MemberDetail`, a `Leveling` page, `wowCharts.ts` (the
  only file that imports Chart.js), and a WoW card in `ModulesAdmin`.

### Linking flow

1. An active member (not a pending applicant) clicks **Link Battle.net** on their own profile.
   mustr redirects to Blizzard with a one-time state cookie, as the Discord login does.
2. On return, mustr exchanges the code, reads the account ID and BattleTag, and lists the
   account's characters in the site's region and namespace. The token is then thrown away; it is
   never stored.
3. The characters are saved with `followed = false`. The member ticks the ones to follow; the
   highest level is preselected as main.
4. Unticked characters are deleted after a day. To follow more later, the member links again.
5. **Unlink** deletes the link, the characters and their timelines at once.

Errors: a denied sign-in, an expired state cookie, or an account with no characters in this
region shows a message on the profile. If the Battle.net account is already linked to another
member, linking is refused.

### Character sweep

- A new cron trigger, `2-59/5 * * * *`, gives the sweep its own 50-request budget, separate from
  the Discord reconcile. It runs whether or not the Discord bot is configured.
- Each run spends at most 40 Blizzard calls (`WOW_CALL_BUDGET`), including any token refresh, and
  makes at most 8 Discord posts (`WOW_POST_BUDGET`), since both count toward the same 50.
- It first spends up to 10 calls on the daily status checks (see retention), then picks followed
  characters by oldest `last_polled_at`. For each one it fetches the summary.
  It fetches equipment only when `last_login_at` changed or the character has no gear yet.
- A 100-character guild refreshes about every 15 to 25 minutes.
- A 429 or 5xx from Blizzard ends the run; the next run carries on. A 404 on one character skips
  it and the run moves on. Only the daily status check (below) can lead to deletion.
- After a run, new events go to medals and Discord (below).

### Change detection

- **First check:** records `baseline_level`, the guild and the gear, and writes one
  `tracking_started` entry. Gear already worn and the current guild produce no entries.
- **Later checks:**
  - **Level:** a higher level writes a `level` row for each level gained.
  - **Gear:** a new item in a slot writes an `item` row, but only for rare quality or better.
    The first rare and first epic ever seen on the character are tagged.
  - **Guild:** a changed guild writes `guild_leave` and/or `guild_join`.
- `seen_at` is the new `last_login_at`; `since_at` is the previous one.
- A lower level, which shouldn't happen, is logged and ignored. Stored state is replaced only after
  the timeline rows are written.

### Badges

Evaluated after each check that changed something.

- **First blue** (`wow:first_rare`): a rare-or-better item is equipped.
- **First purple** (`wow:first_epic`): an epic-or-better item is equipped.
- **All in blue** (`wow:all_rare`): head, shoulders, chest, wrists, hands, waist, legs, feet and
  main hand are all filled, and every equipped item except shirt and tabard is rare or better.
- **Week of the grind** (`wow:week_of_grind`): ten levels within any seven days.
- **Steady climber** (`wow:steady_climber`): a level gained on seven consecutive UTC dates.

The first three can be earned at the first check; the timeline entry then reads "already had it
when tracking started". The last two count only levels mustr saw happen after the baseline. Each
earned badge writes one `badge` timeline row per character.

### Records

Worked out on each request from `level` rows. That's cheap at guild size, so nothing is cached.

- **Reached level L:** the `seen_at` of the character's `level` row for L. It counts only if
  `baseline_level < L`.
- **Standings:** by level, then by who reached that level first.
- **Firsts:** for each L in 10, 20 … 60, the earliest "reached". Everyone within two hours of it
  shares the first.
- **Fastest ten levels:** for each band 10→20 … 50→60, the smallest gap between reaching the start
  and the end, among characters seen reaching both.
- **Scenic route:** the largest such gap across all bands, shown as a friendly nod.
- **Which characters count:** mains only by default. With `alts=1`, every followed character
  counts, for standings and records alike. A member whose main was deleted counts their
  highest-level followed character as main until they choose another.

### Data retention and Blizzard compliance

- Each sweep run starts with a status pass: up to 10 followed characters whose `last_validated_at`
  is more than a day old get a status check. Keeping it in the sweep keeps every Blizzard call in
  one budget; the hourly cron's own budget is already shared with recurring-event Discord calls.
  - Valid with a matching ID: `last_validated_at` is updated and `status_failures` reset.
  - `is_valid` false or a changed ID: the character and its timeline are deleted at once.
  - 404: `status_failures` goes up by one, and the character is deleted on the third consecutive
    failure. A single 404 can mean the player turned off third-party sharing, or a temporary error.
- A DB-only cleanup in the hourly cron, which also runs while the module is off, deletes characters
  not validated in 30 days and unfollowed characters older than a day.
- Unlinking, deleting a member, or deleting a character deletes its rows straight away (cascade).

### Web routes

All under `/api/wow`, all 404 when the module is off.

- `GET /link/start` (member): redirect to Blizzard.
- `GET /link/callback`: finish linking, then redirect to the member's profile.
- `POST /characters/follow` (self): set which characters are followed and which is main.
- `DELETE /link` (self): unlink and delete everything.
- `GET /members/:userId`: a member's characters and timelines. Visible to signed-in members.
- `GET /race?alts=0|1`: standings, records, and each character's level changes with exact times,
  for the charts. Follows the `leveling` page-access setting.
- `GET /admin/config`, `PUT /admin/config`, `POST /admin/test` (settings permission).
- `POST /admin/medals` (medals permission): create the five starter medals.

### Pages

**Profile: Characters section** (when the module is on):

- Cards for followed characters, with a class-colour border, level, item level, guild and last
  online. The main is marked.
- Opening a card shows its journey, grouped by month:
  - Levels from one check are grouped ("Levels 39–40, between 5 and 6 October"), and every tenth
    level is highlighted.
  - Item rows show quality colour, item level and the First epic tag; guild and badge rows appear
    too.
  - Dates read "around 8 October".
- The owner sees **Link Battle.net**, **Choose characters** and **Unlink**.

**`/leveling` page:**

- Built-in menu item with `module: 'wow'`, and a `leveling` entry in page access, default members.
- Header: member count, average level, average item level, and how many were active this week.
- Standings, two charts and the records panel, with an alts toggle.
- **Level over time:** stepped lines in class colours; characters of the same class get different
  dash patterns.
- **Levels gained:** stacked bars.
- **Per day / per week toggle:** the browser groups the exact change times into days or weeks in
  the viewer's time zone.
- Clicking a name in the legend hides or shows that character.
- Chart.js is imported only by `wowCharts.ts` and loads only on this page.

**Admin: World of Warcraft card** in Settings → Modules: the key, region, namespace,
**Test connection**, the last sweep error, and **Create WoW medals**.

### Discord posts

- Two new announcement keys, both off by default, using the existing channel, colour and template
  settings:
  - `wowLevel`: a character reaches a tenth level or 60. Placeholders: `{member}`, `{character}`,
    `{level}`, `{class}`.
  - `wowFirst`: a character is the guild's first to reach a tenth level, or shares it.
    Placeholders: `{member}`, `{character}`, `{level}`.
- Limits:
  - At most one post per character per check. When both apply, `wowFirst` wins if it's switched on.
  - At most 8 posts per sweep run, medal posts included; anything beyond that is skipped.
  - Nothing posts from a first check.
  - Nothing posts for a change whose `seen_at` is more than 24 hours old.
- Badges post through the existing `medalAward` announcement when they become medals.

### Medals

- **Create WoW medals** adds the five starter medals with names, descriptions and their
  `auto_grant_rule`. Admins can rename them or change their pictures like any medal.
- When a character earns a badge, its member gets the matching medal if they don't already hold
  it. The citation names the character, and the award goes through the same path as other medal
  awards, so it's announced and recorded.
- A medal with a WoW rule whose module is off is never awarded automatically.

### Errors

- Blizzard down, busy or rate-limiting: the run stops and the next one carries on.
- One character's error never stops the others, except a 429, which ends the run.
- A bad or revoked key: the sweep stops, and the admin card shows the last error and its time.
- All Discord and medal side effects are best-effort, as the existing announcements are, and never
  undo saved timeline rows.

### Testing

- `npm test` runs `node --import tsx --test` over `src/**/*.test.ts`. No new dependency.
- Unit tests:
  - `diff.ts`: baseline, multi-level jumps, gear quality filtering, first-rare and first-epic
    tags, guild changes, a lower level ignored.
  - `badges.ts`: each badge's edge (exactly ten levels in seven days, a gap in the seven-day
    streak, an empty off-hand with a two-hander), and baseline awards.
  - `records.ts`: the baseline rule, ties within two hours, bands, the scenic route, mains versus
    alts.
  - `bnet.ts` parsing: against the captured Classic fixtures.
- By hand, with the owner's key and the namespace set to Classic:
  1. Link, then follow a character.
  2. Level it a few times.
  3. Check the timeline, the charts in two time zones, the Discord posts and the medals.
  4. Unlink, and confirm everything is deleted.

### Rollout

- Ships with the module off; existing installs see no change.
- When Blizzard publishes Forever's namespace, update the default constant, then switch the module
  on for the owner's guild.
- Roster import and buyer docs follow once the guild has used it.

## Risks and open questions

- **Blizzard may not publish Forever data at launch, or ever.** Mitigation: build and test on
  Classic now and keep the module off until the data exists.
- **Response field names are unverified.** Mitigation: the first plan task captures real responses
  before the parsers are written.
- **10 ms of CPU per run on the free plan.** Parsing up to 40 JSON responses should fit, but it is
  unmeasured. `WOW_CALL_BUDGET` is a constant, so it can be lowered if runs exceed it.
- **Cron count.** A third trigger means three per hosted tenant, so a paid account's 250 triggers
  cover about 83 tenants instead of 125. If that binds, paid tenants can run the WoW sweep inside
  the 5-minute tick, since their request limit is 10,000.
- **Blizzard's terms and the $12/month hosted plan.** Each site uses its own key and the module is
  never a paid add-on. Worth confirming with Blizzard or a lawyer before it's advertised to hosted
  customers.
- **History starts when a member links.** Earlier levels can't be recovered, so late linkers can't
  claim earlier firsts or bands. The page says so.
